# 保持回棋速度的搜索优化与晚期反馈

日期：2026-10-24。用户反馈快速模式棋力不如JS小巫师、后期送子；最终选择“保证速度”，覆盖此前临时选择的“可以更久计算”。

**标准4秒计算预算、自定义1.5秒浅搜及原分帧/附加等待均保留。搜索量有所增加，但本轮没有证明棋力提高，也没有复现并解决用户所指的具体晚期失误。**

## 改动

- 主搜索先试合法的TT/PV及杀手着法，能够截断时跳过其余走法生成和排序。危险节点仍完整生成应对；自定义娱乐浅搜和空步验证路径沿用原策略。
- 用数值棋子颜色快速过滤空格/敌子，复用横向攻击步进表，合并移子的两条哈希与评价差量，减少解释器调用及分配。未改变位置表、终局分或棋规。
- 生产吃将档没有重复评分，停止为每条安静路径分配身份；仍区分pass/null边界并保留可撤销历史。离线标准档继续保留完整重复身份。未来若引入历史评分，须重新扩展缓存依赖。
- 每次真实AI搜索前记录完整棋盘和规则档；回棋日志增加停止原因与分数。下一次送子可提取原局，不增加玩家界面。

## 同预算宿主采样

固定基线`f6e89ed`与候选各测8局面×30/60 FPS，共32次。两引擎预热1200节点，按局面交替测量顺序，双方禁库、采用原4秒逻辑预算，串行执行且无帧间墙钟等待。

- 16组成对结果：候选2组完成深度更深、13组相同、1组更浅。节点数比值的中位数约1.277；排序/缓存会改变搜索树，不能将其等同于棋力提高或通用速度提升27.7%。
- 基线/候选最长宿主step约10.01/10.41ms。现有协作式时间保护不是硬实时保证，本轮没有证明最大8ms或真机帧率达标。
- 局面包含同一历史自对弈的6个黑方快照、1个出库起点和1个手写残局，存在相关性，不是独立封存棋力集。

## JS对照没有达标

同一组8个相关起点交换执色，每手请求100ms，共16局：**2胜、11负、3和、0未决，得分率21.875%**。此前批次为25%；本次没有观察到棋力提升。样本相关、协作式超时及解释器差异均存在，不能据此宣称显著提升或显著退步，更不能称接近小巫师。

Lua/JS完成深度中位数仍为1/2；首轮保底25/0次。Lua最大超出请求时间约5.43ms，JS约9.10ms。报告写入遇到一次Windows临时占用，保留已完成5局后以相同引擎源码恢复；过程差异与实际时间均保留。16局467个半回合已逐步重放，合法性、吃子、最终局面及裁判结果一致。

这项测试使用离线标准档，不能代替生产吃将对手、正式预算400局或真机验收。其引擎模块指纹与最终代码一致；对弈产物是在补充会话日志之前打包，最终完整产物另做下述回归，没有改写旧对弈产物哈希。
