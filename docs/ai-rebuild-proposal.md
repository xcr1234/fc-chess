# 基于 XQWLight JavaScript 1.0 的象棋 AI 完全重写方案

日期：2026-10-24。状态：新内核实现候选已落地（`2ae4417`），规则补充回归通过；直接棋力与真机验收待完成。

## 目标与范围

**CONTRACT：以象棋小巫师 XQWLight JavaScript 1.0 为唯一引擎来源，完整重建 Lua AI，尽力接近该版本在明确规则和计算预算下的棋力。**

- 困难、快速和自定义统一使用新内核，由规则档案适配走法、评价与搜索保护。
- 困难与快速采用相同搜索和预算，差异只在计算完成后的附加等待；自定义允许单独校准预算与选择性优化，以保证极端阵容下响应稳定。
- CONTRACT（用户最新更正）：保持当前回棋速度，本轮标准4秒计算上限与分帧/附加等待策略不增加；不采用已撤回的“延长计算换棋力”选择。
- CONTRACT（2026-10-24最新）：自定义是娱乐模式，采用浅层有限计算，不追求接近小巫师棋力；困难/快速的目标保留。当前自定义默认最多2层、无静态/将军延伸、1.5秒逻辑截止、2000节点、关闭TT。实际吃将及立即失将检查先于浅层静态估计；该估计不作为完整战术搜索的精确缓存值。详见[调整用例](../tests/ai-custom-light-plan.md)。
- 重新实现局面结构、走法生成、攻击检测、走子撤销、评价、排序、置换表、搜索、分帧调度和开局库运行时适配。
- 游戏会话、界面与 `new / step / cancel` 接口按现有产品契约接入；复用接口不等于复用其内部算法。
- 保留实际吃将、允许送将和不应将、飞将、无基本着法跳过，以及自定义自由士相等玩法。
- 下述条目描述目标架构与验收要求；实际已取得的实现/测试证据以文末交付状态及生产进度为准。

## 新引擎结构

会话 → 新 AI 门面 → 规则档案 + 新局面/搜索内核 → 完整结果 → 共用等待 → 版本与合法性复核 → 实际落子。

| 模块 | 职责 |
|---|---|
| `game.ai` | 新任务门面，保留 `new / step / cancel` 接入形式 |
| `game.ai.rules` | 规则档案、基本走法约束、终局与真实跳过语义 |
| `game.ai.position` | 256 格内部棋盘、数值棋子、整数着法、增量状态、走子撤销 |
| `game.ai.movegen` | 走法生成、攻击检测、立即吃将和安全应对识别 |
| `game.ai.evaluate` | JS 1.0 位置表评价、自定义规则扩展 |
| `game.ai.order` | PV/TT、吃子、杀手与历史排序 |
| `game.ai.tt` | 固定容量、签名、深度/代次替换、分数界限 |
| `game.ai.search` | 完整窗口参考搜索、PVS、静态搜索、延伸、空步验证 |
| `game.ai.scheduler` | 可恢复任务、切片、截止、取消与诊断 |
| `game.ai.book` | 同源 JS 书库数据的查询、过滤、种子选择 |

上述模块均按 JS 1.0 基线重新实现。外部 90 格棋盘在任务开始时转换一次，结果提交时转换回现有坐标；搜索内部不反复转换。共享状态、缓存和历史均由任务/会话明确持有，模块内部状态使用 local。

规则档案分为：

- `reference-standard-v1`：仅离线测试，复现 JS 1.0 的标准安全走法与重复评分。
- `casual-capture-v1`：困难/快速的实际吃将规则。
- `custom-capture-free-advisor-elephant-v1`：自定义实际吃将规则，红士不限九宫、红相可过河且检查象眼，黑方士相保持普通范围。

生产模式只按规则档案配置同一新内核。自定义恢复原始阵容后仍使用自定义档；不同档案不共用 TT。离线标准档不新增玩家入口。

## 游戏规则适配

JS 1.0 的 `makeMove` 拒绝自将，静态搜索和延伸依赖该前提；因此必须同时适配生成、危险识别、终局、重复和静态搜索。

生产吃将档的节点处理顺序：

1. 检查已经发生的将帅被吃，终局分优先于静态评价。
2. 检查当前方能否立即吃敌将，包含飞将；可吃即返回一步胜利。
3. 生成该档案的全部基本着法，保留玩家可以执行的送将着。
4. 非吃将着若走后允许对方立即吃己将，搜索可直接返回对应失将距离分，省去后续展开。
5. 只有不安全基本着时，仍返回可执行着法；实际对局等待真实吃将，不提前结算。
6. 没有基本着才执行真实跳过；双方均无基本着返回无法继续状态，不能无限互相跳过。

己将受攻击时仍可能先吃敌将获胜，所以主搜索、静态搜索、书库过滤和根保底都必须先检查立即吃将。攻击检测使用本档案的几何走法和挡子规则；攻击者走后暴露己将不影响其先吃将获胜。

将帅照面本身不结束游戏；立即吃将、下一手失将与已被吃将的距离分须统一。玩家允许送将不代表 AI 忽略对手最佳应对。吃将档与标准档的无着、重复和终局时机不同，不能无条件要求整局评分一致。

### 自定义适配

- 新生成器与攻击检测直接支持 1 帅 15 车、自由士相和炮架变化；不使用每种棋子最多两枚的固定身份表。
- 自定义同样使用新搜索与调度，可关闭未经验证的空步等优化，单独校准资源保护；不承担与困难/快速相同的胜率目标。
- 自定义娱乐策略到达深度边界即停止，不要求将危险叶子展开至安静；这是明确的浅层估计。下文危险叶子必须继续应对或中止的完整战术要求适用于困难/快速及离线完整搜索，不用于强迫自定义继续计算。
- JS 普通位置表未覆盖的自由士相活动格必须定义有界扩展评价，不能将表外零值当作棋子没有价值；材料分和位置分拆分方式须与标准表的总尺度一致。
- 自定义禁用标准开局库；终局分高于极端阵容的全部非终局评价，根着法缓冲覆盖极端分支数。

## 局面、评价与缓存

### 局面与评价

- 以 JS 1.0 的 256 格邮箱、数值棋子和整数着法为内部基线，预计算棋盘、九宫、过河与步进信息。
- 走子/撤销增量维护棋子、将帅位置、子力位置分、行棋权、哈希与历史；与全量重算逐局面对照。
- 标准评价先忠实保留 `PIECE_VALUE`、红黑坐标翻转、行棋权项和评分尺度。表内已包含子力意义，不能重复叠加材料分。
- 先完成基线复现，再逐项实验阶段权重、机动性、炮架、兵推进或士相防守；每项均测时间、封存解题集与对弈收益。
- 着法、排序和栈缓冲复用；避免节点内拼全盘字符串、深拷贝、生成大量临时表或反复创建闭包。

### 哈希与置换表

- 使用确定性 Zobrist 主键与校验键；先验证目标 Lua 和 JS/Fengari 的位宽行为，不默认 64 位整数可直接互通。
- TT 先测 16K/32K/64K 槽的内存和耗时，按签名、深度、界限和代次替换；不因计数达到阈值整表清空。
- exact/lower/upper 分开；中止节点不写精确分；不兼容条目最多提供已复核的排序着。
- 胜负距离分用局部变量在存取时归一化。同一条目重复读取不能改变缓存分数；已有 JS 源码探针识别的读取漂移须用独立回归覆盖，上游原样与修正基准分别标记。
- 主/静态搜索、剩余延伸配额、叶子策略和历史依赖必须进入值复用条件；相同棋盘键不代表节点语义相同。
- 路径重复产生的分数及受其影响的父节点值不能当作与路径无关的 TT 界限。悔棋、重开和规则变化须恢复或失效相关缓存。
- 当前生产档不执行重复评分或循环偏好，缓存路径环境只保留pass/null边界，不为每条安静路径分配身份；离线标准档保留完整历史身份。若以后引入历史评分，必须同步恢复相应依赖签名。

## 搜索实现顺序

### 正确性基线

先实现完整窗口 Negamax Alpha-beta，再逐项开启 PVS、排序和 TT。固定深度对照使用相同规则、评价、静态搜索、延伸配额、历史、空缓存和确定性参数，不允许预算中止。校验模式仅复用相同剩余深度及叶子语义的缓存值。

比较精确根分与独立完整窗口确认的最优着集合，允许同分着不同；上下界不能作为精确值比较。离线参考版可同步运行，生产搜索使用可恢复任务；相同工作预算下验证切片/恢复与同步结果一致。

### 静态搜索与延伸

- 安全节点允许静态停搜，并展开相关吃子；己将危险时优先检查反吃敌将，再展开全部安全应对，包括安静挡线与逃离。
- 将军/唯一安全应对延伸是基线能力，“唯一”按剔除立即失将着后的应对数判断。
- 静态搜索和延伸均计入总预算，设置路径延伸配额与最大总层数。危险节点触及保护时传播中止，不能将静态分包装成可靠精确分。
- 吃子排序先复现 JS 1.0；SEE 作为后续独立实验，不能在每个叶子默认全盘计算风险。将军、解危与吃将相关着首版不做 SEE/差值剪枝。
- 战术判断允许合理弃子和反击，不添加被捉必跑或某棋种不得交换的禁令。

### 空步验证

空步及验证搜索属于 JS 1.0 基线的必做移植与对照项；正确性校验时关闭，完成安全测试后决定生产默认。

1. 非根、非 PV、当前安全且深度与可用子力足够时试验；禁止连续空步，先排除少子等着、真实无着跳过与临近胜负界限局面。
2. 试探失败高分须经过禁空步验证后才允许截断；阈值使用 JS 评价尺度并通过实验校准。
3. 空步与真实跳过分别维护走子权、哈希、路径和撤销；取消可以发生在试探、验证和重搜之间。
4. 通过残局/等着/循环/强制杀与吃将回归后，比较有/无空步的同时间解题及对弈；无收益或误判则关闭并记录依据。

LMR、futility、delta pruning 等作为后续独立实验，不与基础移植同时引入。

### 重复与优势兑现

离线标准档复现 JS 1.0 的 `repStatus/repValue`。生产吃将档保留真实对局历史和搜索路径，不将重复自动结算为和棋或长将判负。

在测试设计阶段固定循环启发、触发次数与历史窗口，比较无偏好与历史感知策略，覆盖优势脱离、劣势重复、唯一救命重复和连续将军；不能无条件禁重复。书库同样执行该历史政策，悔棋恢复。有限搜索、循环率与优势兑现率分别验收。

## 分帧调度与开局库

- 搜索、静态搜索、空步验证、PVS 重搜及重操作均可恢复；初始化、根排序、书库冷查找和取消恢复纳入测量。
- 同时保留节点、总层数与总耗时保护，数值由新内核实测确定。若官方提供足够精细的单调时钟，以帧内时间预算辅以工作量上限；否则校准操作配额，不虚构毫秒级抢占。
- HYPOTHESIS：AI 帧内工作 P95 ≤4ms、最大 ≤8ms，须真机校准；同时记录按钮响应、整帧耗时、GC 和内存。
- 测试 1/2/4/8 秒计算预算曲线，按实际棋力与响应选择上线配置；实验档不自动改变产品等待。困难/快速同政策，附加等待期间不继续搜索。
- 每轮完整完成后提交结果。中止取上一完整轮；首轮未完成用吃将优先、安全优先的已验证保底。取消、悔棋、离局完整恢复工作状态，过期任务不能落子。
- 使用同一固定 JS 版本的书库数据和权重，重新实现查询、镜像、候选过滤与种子选择。可复用该来源已转换的数据，但须重新通过新内核验证。
- 按完整局面、行棋方与规则档匹配，直接吃将优先；无有效书着正常搜索。种子只在实际提交时推进，悔棋恢复。

## 验收要求

### 必测行为

- 炮架、马腿、象眼、飞将、双攻、连续回吃、合理弃子、安静防守及车马炮兵残局配合。
- 己将受攻击但可先吃敌将、送将后立即吃将、被迫失将但尚未结束、单方真实跳过与双方无法继续。
- 自定义 15 车、自由士相攻击与位置评价、同类棋子数量、根着法容量和标准书库隔离。
- TT 签名碰撞、上下界、胜负距离可逆、重复读取不漂移、延伸/静态/历史语义隔离。
- 静态危险节点、空步验证、PVS 重搜中预算耗尽或取消；棋盘、增量分、哈希、历史与种子完整恢复。
- 搜索/等待中悔棋、菜单/重开、确认阻挡、过期结果丢弃与困难/快速同条件同结果。

### 三层对照

| 层次 | 对照 | 目的 |
|---|---|---|
| 算法复现 | 离线标准档 Lua 对固定 JS 1.0；关闭随机/书库与选择性裁剪，统一叶子/延伸语义 | 检查生成、评价、搜索与移植行为 |
| 实际棋力 | 标准档对 JS 1.0，生产吃将档对 JS 1.0 吃将适配基线 | 测量直接棋力差距与玩法适配成本 |
| 平台可用性 | 同一新产物在目标真机预算/切片下回放局面并与对应基线比较 | 验证实际可用棋力、输入响应与资源消耗 |

JS 吃将适配基线只按书面契约修改终局、直接失将、真实跳过和重复语义，保留 JS 搜索与评价核心；适配器独立验证并保留补丁，不与 Lua 候选共享搜索实现。报告区分原版、适配版和已知缺陷修正版。

JS `searchMain` 在完成一轮后才检查时限。时间赛双方必须采用已记录的实际硬截止与完整迭代保底，初始化、表分配、GC 和切片间隔的口径一致；未改截止的 JS 原样版另列真实耗时与超时率。Node/JS、Fengari 与真机 Lua 的吞吐不同，结果必须注明宿主和预算。固定深度用于行为对照，同节点用于已统一计数定义的效率比较，均不代替同时间棋力。

### 建议量化门槛

以下均为 HYPOTHESIS，尚未取得实测结果：

1. 至少 120 个固定局面，覆盖战术、安静中局与残局；至少 40 个封存不参与调参，镜像和相邻棋谱不跨训练/验收集。每例标明规则档、可接受着集合或战术结果及依据。
2. 规则、撤销、取消和必测行为全部通过；封存集解题率目标达到对应 JS 基线的 95% 以上，并分别报告战术/残局与严重漏吃、送将和送子情况。基线未解出的题单列，不能作为候选必错的真值。
3. 标准档与吃将档各使用至少 200 个独立起始局面，交换执色至少 400 局；固定版本、规则、时限、缓存、历史和 seed。对对应 JS 基线的得分率目标 ≥40%，以起始局面成对重采样的 95% 区间下界目标 ≥35%；这是项目自定的接近门槛，达标后继续缩小差距。
4. 对弈关闭双方书库以测出库棋力；另以同一书库/种子做整局回归。标准测试赛采用明确的简化裁判：无安全合法着负、同一行棋方的完整局面第三次出现和，不额外执行赛事长捉裁判；搜索内部重复评分单列。吃将赛仅按产品实际结果结算，重复不能记和。
5. 两类对弈预先固定 300 半回合上限，超限或无法继续且无赢家记未决 U。保留 W/L/D/U 和完整棋谱；N 场得分区间为 `[(W+0.5D)/N, (W+0.5D+U)/N]`，通过以保守端及其置信下界判断，不删除未决或默认为半分。
6. 报告完整深度分布、主/静态节点、总计算时间、帧内耗时、内存、循环率和优势兑现率。仅提高配置深度不算达标；离线通过且真机未通过时，状态仍为候选。
