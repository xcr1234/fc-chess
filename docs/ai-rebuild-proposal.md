# 象棋 AI 第二次重写设计方案

日期：2026-10-24。状态：按“尽力接近象棋小巫师棋力”复审后的设计提案，尚未实现，也未改变现行 GDD 棋规。

## 结论与范围

建议以固定版本的象棋小巫师 XQWLight 为基线，先复现其局面、评价与搜索行为，再完成吃将规则适配和 Lua 分帧移植，重建困难/快速模式的引擎；自定义模式继续使用当前娱乐引擎。困难与快速保持相同计算策略，仍只在计算后的附加等待上有区别。

**目标升级为：在明确的对照版本、相同规则和已记录的资源条件下，测量并缩小与小巫师的棋力差距。胜过旧版、达到某个深度或拥有同名算法，都不足以验收这个目标。** 实施顺序以减少与成熟基线的偏差为先，不重新凭经验拼一套评价后仅借用小巫师的搜索名称。

**推荐优先保留送将、不应将、实际吃将结算。算法能够支持，代价是需要明确改造规则相关的搜索逻辑，不能直接翻译上游。** 若后续希望尽量贴近上游并降低验证成本，可另选禁止自将、强制应将的路线；它还涉及将死、困毙和重复局面规则，不能只切换一个检查函数。

本轮只提交设计及未来验收要求，不编写生产实现、不修改存档、不构建或运行模拟器。本方案允许自定义使用不同棋力，是用户本轮放宽的范围；现有文档中的“三模式共用棋力”在未来实施时需同步修订。困难与快速的等棋力要求不变。

## 本次复审发现与修订

| 优先级 | 原方案的缺口 | 对棋力目标的影响与本次修订 |

| P1 | 位置评价仍打算自行重建，空步仅作为可选后续项 | 同时改变评价与搜索，失败时难定位；先保留上游位置表/评分尺度，空步验证列为必做实验，生产启用以结果为准 |

当前源码与记录支持以下判断：

- 搜索已经是 PVS，再重写一遍 PVS 本身不会自动解决问题。
- `search.lua` 每帧最多进入 16 个节点，累计 `dt` 达到 4 秒停止。30 FPS 时理论节点上界约 1920，实际还受栈操作和开销影响；60 FPS 时通常先受 3200 总节点限制。帧率会影响搜索量。
- `board.key` 每节点拼接完整棋盘字符串；着法、搜索帧和排序产生较多临时表；TT 达到计数阈值后整表清空，难以稳定保留有价值结果。
- 当前叶子同时计算双方受攻击子力风险，内部生成吃子并计算交换链。该启发有用，但把昂贵计算放在大量叶子上，会挤占更深搜索的机会。
- 静态搜索额外限制 2 层，复杂交换、安静威胁和后续回吃仍可能超过视野。历史尝试直接加到 4 层导致 15 车局无法完成首轮，说明极端模式正影响公共参数选择。
- 真实炮换马案例在完整 2 层下也选择同着，不能归因为“完全漏算红车回吃”。浅层评价偏差与搜索量不足需分别处理。

历史性能记录 `records/ai-exchange-performance-final.txt` 的 3 个 Fengari 样本，单步 P95 约 41–52ms，最大约 77ms；记录明确存在并行任务干扰。这是性能风险信号，不能视为真机指标或严格速度对比。本轮未重新跑性能或胜率测试。

上游 `makeMove` 走子后通过 `checked()` 拒绝自将；`searchQuiesc` 在被将时搜索应对，否则允许静态停搜；`searchFull` 使用重复局面、空步和延伸。这些互相依赖。只移除自将检查，会留下错误的终局/叶子假设。

上游 `checked()` 在标准规则下不必处理自由士相对敌将的攻击。不能将其直接当作自定义模式的通用攻击检测器。其位置表和空步阈值也不能直接用于 15 车或自由士相。

“忠实复现”也不等于机械复制已发现的问题。本轮对 JS `probeHash` 做了一次离线函数探针：同一条 `vl=9950`、当前 `distance=3` 的命中，连续读取返回 `9947`、`9944`，缓存值也变成 `9944`。原因是读取时直接修改了缓存中的胜负距离分。Lua 必须用局部变量归一化，重复读取不能漂移；上游原样版与修正版分开保留，报告采用哪版，不能悄悄修弱或修强对手。该探针没有运行对局，不是棋力测试。

## 规则支持与推荐路线

| 需求 | 小巫师原版 | 本方案 |
|---|---|---|
| 送将、不应将 | 不支持，`makeMove` 拒绝自将 | 新引擎明确支持，搜索把立即失将识别为失败变化 |
| 能吃将但选择其他走法 | 按标准规则处理，不能直接等同 | 玩家保留自由；AI 优先选择立即胜利 |
| 将帅照面、飞将实际吃子 | 标准安全判断与当前裁判语义不同 | 单独实现飞将吃子，照面本身不结束游戏 |
| 无基本走法自动跳过 | 无合法着通常返回败分 | 保留当前跳过语义；双方均无着返回无法继续状态 |
| 重复、长将、长捉不自动结算 | 有重复/连续将军相关搜索评分 | 不移植为游戏裁判；独立控制搜索的有限性 |
| 1 帅 15 车 | 不保证生成容量、评价及剪枝全部适配 | 自定义走旧引擎，沿用现有覆盖，另验吞吐和兜底 |
| 红士出宫、红相过河且仍塞象眼 | 原版活动范围不支持 | 自定义沿用现有规则，黑方士相仍保持普通范围 |

### 推荐：吃将规则 + 新引擎

必须区分“玩家可以这样走”和“AI 认为这样走有利”。支持送将不意味着 AI 必须主动送将；搜索应预测对手会选择最佳应对。

搜索节点按以下顺序处理：

1. 检查已经发生的将帅被吃终局，终局分优先于所有静态评价。
2. 检查当前行棋方是否能直接吃对方将帅，包含飞将；能则为一步胜利。
3. 生成基本着法。玩家允许的送将着仍属于规则合法着法。
4. 在搜索内部，非吃将着若走后允许对手立即吃己将，可直接记为下一手败分，省去继续展开。这是可证明的战术结论，不是禁止玩家落子。
5. 若没有安全着法但存在基本着法，按下一手失将评价，同时返回可执行着法；实际对局仍等待对手真的吃将，不能提前宣告败局。
6. 没有基本着法才按现有规则切换行棋方；双方均无着要返回特殊状态，不能无限互相跳过。

关键反例：自己受攻击时仍可能先吃掉敌将获胜。因此必须“先检查直接吃将，再判断己将危险”，不能简单强制所有变化先解将。该处理应在主搜索、静态搜索、根保底和书库筛选中一致。

攻击检测按当前档案的几何走法与挡子规则判断，不因攻击者走后会暴露其将帅就忽略它：在实际吃将玩法中，先吃将已经结束。不能用标准版“安全合法着”生成器替代这个检测。立即胜利、被迫下一手失将和已被吃将的距离分也要统一，避免快赢/慢输排序及 TT 归一化错一手。

这能减少很多无意义的送将分支，但**不使吃将规则与标准象棋完全等价**：无着处理、真实终局时机、重复规则仍然不同。对应标准合法局面上的走法集合可以对照上游，整局评分不能无条件要求一致。

### 备选：采用标准合法着法

如果更看重降低改造成本，可以让困难/快速禁止自将、必须应将，并禁止将帅照面。还必须明确：将死与困毙是否直接判负、重复局面如何处理、是否接受简化裁判。小巫师的重复处理也不能当作完整赛事规则实现。

这条路线更方便与上游做完整搜索对照，但不是提升棋力的必要前提。建议先保留当前玩法；只有规则适配成本或基准结果不理想时，再由用户选择是否改变体验，不在实施时悄悄切换。

## 新引擎结构

界面/会话 → 引擎路由 → 标准阵容新引擎或自定义旧引擎 → 统一结果 → 共用等待 → 版本与合法性复核 → 实际落子。

建议新增模块职责如下，实际命名可在实现阶段调整：

| 模块 | 职责 |
|---|---|
| `game.ai` | 保持 `new / step / cancel` 任务接口，按规则档案选择引擎 |
| `game.ai.position` | 内部棋盘、数值编码、增量哈希/评价、完整走子撤销 |
| `game.ai.movegen` | 基本走法、目标格攻击检测、飞将和立即吃将检测 |
| `game.ai.evaluate` | 子力/位置、阶段性评价及小成本附加项 |
| `game.ai.order` | TT/PV、吃子排序、杀手与历史启发 |
| `game.ai.tt` | 固定容量、签名校验、深度/代次替换、分数界限 |
| `game.ai.search` | 主搜索、静态搜索、延伸和完整迭代提交 |
| `game.ai.scheduler` | 工作切片、预算、中止、恢复与诊断 |
| `game.ai.legacy` | 冻结当前娱乐搜索及交换评估，服务全部自定义局 |

外部仍使用现有 90 格棋盘，任务开始时转换一次；搜索中不反复转换。最终结果转换回现有坐标，保留悔棋、种子、最近落子框和等待接口。为旧引擎保留其依赖，不让新评估模块的调整暗中改变娱乐模式。

另保留仅离线测试使用的上游标准规则档，用于复现小巫师及移植对照，不在模式菜单增加入口，也不改变玩家落子规则。生产路由只使用标准阵容吃将档与自定义旧引擎；标准测试档的规则、缓存与历史均隔离。

不按“当前盘面看起来标准”选择引擎。自定义即使恢复初始棋子，红士相仍有自由规则，仍应走旧引擎。规则档案、引擎版本和缓存代次分离；不同规则不共用 TT。书库可复用已有完整局面数据，但候选必须经过本档案的直接吃将优先和安全复核。

### 数据与缓存

- 首选 256 格邮箱结构，预计算棋盘/九宫/过河信息及棋子步进；不以某棋种固定两个身份编号表示棋子。
- Zobrist 使用确定性初始化，增量维护主键和校验键。Lua 整数、位运算和 JS/Fengari 对照的位宽必须先做小测试，不能默认 64 位键在所有宿主一致。
- 着法与各层缓冲复用；避免每个着法建立小表、每节点重新构造排序闭包或拼接棋盘键。
- TT 初始候选容量为 16K/32K/64K 槽，通过实际内存和耗时选型；不是已确定的上线配置。不按 C 结构体字节数估算 Lua table 内存。
- 深度与代次决定替换，不因达到阈值整表清空；只有签名匹配才复用界限。胜负距离分在存取时归一化，中止节点不写精确分。
- 主搜索与静态搜索的缓存策略分开；剩余延伸配额、静态搜索截断策略等会改变节点含义，值复用条件必须覆盖这些差异。不兼容的条目最多提供经过复核的排序着，不能只凭更深就复用分数。
- 重复路径相关结果不能仅用棋盘键当作通用精确值缓存；通过父节点传播的路径依赖分数同样受限。只禁止在重复叶子写缓存不够。
- 测试从空缓存起步；是否跨回合保留 TT/历史表作为后续独立实验。若保留，悔棋/重开必须失效或正确恢复，不能用上局历史污染本局。

### 重复局面与兑现优势

保证有限搜索只是底线，不能作为循环问题已经解决的证据。新引擎接入时，任务输入应包含已提交棋局的相关历史与搜索路径，悔棋同步恢复；书库也使用同一历史政策。

- 标准测试档复现上游 `repStatus/repValue`，包括连续将军的搜索评分；这只是该软件的规则基线，不称为完整赛事裁判。
- 生产吃将档不把重复局面自动结算为和棋或长将判负。先比较不加循环偏好与历史感知的循环评分：后者可用受限的搜索启发/同分避重复，不能把上游禁着败分照搬过来，也不能无条件禁止重复而放弃唯一救命手。
- 最终循环评分、触发次数和历史窗口在步骤 2 写成明确契约后才实现；必须覆盖优势主动脱离、劣势允许合理重复、唯一安全重复、连续将军，以及“重复后仍能走并实际吃将”。
- 重复截断及受它影响的搜索值不得作为与路径无关的 TT 界限。主深度、延伸配额、最大总层数仍是安全保护。

若无法证明新循环启发改善对局，可暂用无偏好策略，但必须报告循环率和优势兑现缺口，不能据此宣称吃将档已接近上游。

### 搜索与中残局评价

先构建不带选择性裁剪的完整窗口 Alpha-beta 参考版；PVS、TT、排序逐项开启，与参考版比对固定深度分数。对照必须使用同规则、评价、静态搜索、延伸配额、历史、初始缓存及确定性参数，不允许预算中止；校验模式仅复用相同剩余深度和叶子语义的 TT 值，避免较深缓存改变名义固定深度结果。允许同分最佳着不同，但根分应一致，着法须在独立完整窗口确认的最优集合内。上下界不能当成精确分逐项比较。测试参考版可同步运行，正式任务仍需分帧。

静态搜索从“固定再搜 2 层”改为“搜索未稳定的吃子及必要解危，受总预算和最大总层数约束”。安全节点允许静态停搜；己将受攻击时不可直接以静态分停搜，必须搜索逃离、吃攻击子、挡线等全部安全应对，并优先检查反吃敌将。只搜吃子会漏掉安静防守。将军/唯一安全应对延伸作为基线必做项；“唯一”按剔除立即失将后的应对数计算，不按基本着总数计算。延伸设独立路径总配额，避免每步将军使深度永不减少。危险节点触及资源/总层数保护时传播中止，不把静态分包装成可靠精确分；循环按前述历史政策处理。一般安静威胁延伸不自动加入基线，后续另做对照。

评价采用分层增加：

1. **上游评价基线**：先保留 `PIECE_VALUE` 各表、红黑坐标翻转、行棋权项和增量维护，与全量重算、上游输出逐局面对照。表内已经包含子力和位置意义，不能再重复叠加旧版 `R=900/N=400/C=450` 等材料分；空步阈值、排序及其他权重统一用该尺度。吃将终局分另设并确保大于所有非终局分。这一步不沿用旧引擎昂贵的全盘受攻击子力风险。
2. **中残局增量改进**：稳定基线后，再试按剩余主要子力平滑切换位置权重，或增加兵的推进/通路与将帅关系、车的活动线、马腿与活动性、炮架及残局炮的有效性、士相防守。它们是可能的改进，不是“复现小巫师”之前必须重做一整套的前提。每项分别测耗时、独立解题集与对弈，不能只以静态分看起来合理验收。
3. **交换估计**：先用上游吃子排序作为参照；SEE 只在实测有收益时用于排序，再考虑保守剪枝。不默认每个叶子都全盘计算双方风险。象棋炮架、闪击和将帅终局使最低价值攻击者交换估计存在边界，不能把 SEE 当成全局最优结果；将军、解危、吃将相关着首版不做 SEE/差值剪枝。

保留当前“炮换马”及捉子回归，允许引擎通过搜索找到合理弃子反击；不添加“被捉必跑”“炮不得换马”一类禁令。

### 空步与选择性搜索的上线顺序

关闭空步是正确性校验手段，不是接近小巫师的最终能力清单。上游 `searchFull` 使用空步、子力门槛及必要的验证搜索，本方案必须完成有/无空步的对照实验；不能把尚未测试的功能永久留在“以后再说”。

1. 先用无空步、无激进减深版本通过完整窗口/PVS/TT 和吃将规则正确性测试。
2. 接入可开关空步：仅非根、非 PV、当前安全、深度与可用子力足够的节点试验；禁止连续空步，先禁用于少子、等着、真实无着跳过及临近胜负界限局面，失败高分必须经过禁空步验证后才允许截断。具体阈值来自已固定评价尺度及实验，不沿用旧材料分猜数。
3. 空步不是游戏中的“无基本着法自动跳过”，其走子权、哈希、路径、层数与撤销状态分别维护；取消可能发生在空步试探、验证及重搜之间。
4. 通过等着/残局/循环/吃将回归，再以独立时间基准比较解题与对弈。若空步有收益则进入候选默认；若无收益或误判，记录数据后关闭，不能以“用了空步”作为达标条件。
5. LMR、futility、delta pruning 等不属于这一轮必需移植项；只有上述基线仍有明确瓶颈时再逐项实验，不同时加入多种裁剪掩盖问题。

### 预算与平台调度

重写的核心目标之一是减少单节点成本，而非单纯提高节点上限。每帧 16 节点并不能约束一帧真实耗时，因为生成、排序、评价可能很贵。

- 正式接口采用可恢复显式栈，涵盖搜索、静态搜索和重搜；重操作也需能够拆分，任务初始化/根排序/书库冷查找计入性能测量。
- 保留节点、总层数和总时间保护。若平台有经核验的足够精细单调时钟，以帧内时间预算辅以工作量上限；若没有，按最坏局面校准操作配额，不虚构毫秒级控制。
- 建议试验目标：AI 帧内工作 P95 不超过 4ms、最大不超过 8ms；这只是待真机校准目标，不能保证所有设备达到。按钮响应和整帧耗时同时测量。
- 先测 1/2/4/8 秒计算预算的棋力与吞吐曲线，4 秒为现行体验参照，8 秒只是离线/设备实验档，不在本次设计审查中改变产品等待。若 4 秒差距显著，分清节点成本、切片空闲、裁剪或预算瓶颈，再提出有数据的体验调整。
- 不继承旧版 3200 节点与 6 层作为新引擎的生产天花板；按最强可用且满足响应目标的配置校准保护上限。目标不是刚好过 4 层，实际深度只作诊断，最终由对小巫师的表现验收。
- 困难/快速使用同一政策；困难的故意等待不转成额外搜索时间。固定 TT 容量、表初始化、冷查库、状态恢复与 GC 停顿都计入端到端耗时；不能只报告搜索循环内的节点速度。
- 固定节点基准用于复现与算法对比；时间预算基准用于真实体验比较。不同帧率/设备触发时间保护时可能得到不同深度，不承诺跨设备逐手一致。
- 输出最近完整迭代，未完成首轮时用预先检查的吃将优先、安全优先保底。取消、悔棋、返回菜单必须完整恢复工作棋盘，旧任务不能提交结果。

## 自定义娱乐模式

首选冻结旧引擎，仅经路由和兼容适配继续使用。理由是它已经覆盖 15 车、出宫士和过河相，重写普通模式时无需再次承担这些规则变化。旧版性能风险仍在，不能将“沿用”表述为已满足帧预算。

如果后续要简化，可替换为有界 1–2 层搜索加有限交换判断：立即吃将 → 避免被立即吃将 → 子力/吃子/基础位置评分，始终对双方使用自定义真实走法。不能只做“吃价值最高的子”，否则会再次出现容易观察的送子。此路线接受较弱棋力，以稳定响应和合法落子为优先。

首版自定义禁用标准开局库，不承担与新引擎相同胜率目标。根着法容量不可沿用标准局面的估计；总子数仍为双方各 16，变化的是同类棋子数量和分支数。胜负分始终大于极端子力总评价，不能用普通子力优势覆盖吃将。

### 对照分三层，不能互相代替

| 层次 | 对照双方与条件 | 能回答的问题 |
|---|---|---|
| 1：移植与算法 | 离线标准档 Lua 对固定 JS 小巫师；相同局面/历史/评价/静态与延伸政策，先关闭空步/随机/书库做固定深度，再开启各项 | 是否遗漏或改坏了上游核心能力；关闭选择性优化时可要求精确根分相等 |
| 2：实际吃将棋力 | 生产吃将档对 JS 吃将适配基线；双方共享书面规则契约，适配器独立验证，不共享候选的搜索实现 | 规则适配后是否仍保持目标水平，是否会送将、循环或无法兑现优势 |
| 3：平台可用棋力 | 同一候选产物在目标真机实际计算预算/切片下回放局面，记录结果再与对应参考基线比较 | 实际设备是否有足够吞吐支撑离线棋力，以及交互、内存是否合格 |

第 2 层的 JS 适配基线保留已固定的小巫师评价与搜索核心，只按契约修改吃将、直接失将、真实跳过和重复语义，并保存补丁及每项适配用例。它必须明确称为“吃将适配基线”，不能冒充未修改原版。第 1 层另测标准档对原版的成对对弈，第 2 层另测吃将对弈；两组结果都达标才支持“在该基准条件下接近 JS 版”的表述。

固定节点只适合核对相同节点计数定义下的算法效率；不同选择性搜索不能据此直接排名棋力。固定深度用于复现行为，不能单独代替棋力。相同宿主时间预算用于软件对比，但 Node/JS、Fengari 和真机 Lua 的运行速度不同；原生 Win32 0.6 的同时间比较另列。报告必须写清“接近哪个版本、在哪个平台、什么规则及预算”，不合并成无条件结论。

上游原版 `searchMain` 在完成一轮后才检查时限，可能超出请求时间。时间赛不能只给两边同一个 `millis` 就称公平：双方须在实际硬截止内输出已完成迭代/合法保底，上游也要有被记录的中止适配；未加硬截止的原样版只作为另列参照，报告真实耗时和超时率。分配 TT/加载/GC 与分帧间隔的计时口径也必须一致。基准关闭双方书库以隔离出库棋力；另开同一书库/种子的整局回归。

### 候选门槛与接近目标

**以下均为 HYPOTHESIS / 建议验收标准，不是本轮测得结果：**

1. 规则、撤销、取消与现有确定性回归全部通过；对指定走法的断言应核验是否排除了合理替代，不能仅因不同着法判错。
2. 建立至少 120 个固定局面：真实失败、战术、中局安静选择与残局均有覆盖；至少 40 个封存为不参与调参的验收集，镜像/邻近棋谱不能跨训练与验收集。每例标注可接受着法集合或战术结果、规则档与依据；上游单次建议不能直接当作娱乐规则真值。
3. 在同一独占宿主与同一时间政策下，报告解题率、严重漏吃/送子率、完整深度分布、主/静态节点量、帧耗时、内存，以及循环率和优势兑现率。最低 4 个半回合仅作早期诊断，不是完成标准。建议目标为封存集总体解题率达到对应上游基线的 95% 以上，并分列战术与残局，不能用容易的开局题抵消严重战术回归。
4. 固定至少 50 个出库局面，交换执色进行至少 100 局新旧对弈，候选得分率目标 ≥65%；这只是是否优于旧版的门槛。开发测试可双向执色，不要求增加玩家执黑功能。
5. **接近目标的直接验收**：第 1、2 层各使用至少 200 个未用于调参的起始局面，交换执色共至少 400 局；覆盖平衡中局与残局，固定版本、时限、缓存容量、硬截止、历史及 seed。同条件对对应小巫师基线，建议得分率目标 ≥40%，并报告以起始局面为单位成对重采样的 95% 置信区间，区间下界建议 ≥35%。Win32 0.6 在同一开发宿主、相同实际计算时长下另做至少 400 局标准档对照，力争相同门槛；目标真机另报其实际切片下对参考着法/局面的表现，不伪装成同宿主速度比较。这是项目自定的“接近”门槛，并非棋界通用评级，更不是承诺；达标后仍继续以缩小差距为优化方向，不能用此门槛代替全部回归。
6. 所有对弈保留 W/L/D/U（胜/负/按基准真实结算的和局/未决）与完整棋谱。标准测试赛采用明确的简化裁判：无安全合法着判负、相同行棋方的完整局面第三次出现判和，不另执行赛事长捉裁判；搜索内部仍保留其自身重复评分。两种规则赛均预先固定 300 个半回合上限，超出为 U。吃将赛只按实际吃将或双方无着等产品结果处理，重复不能记 D，无法继续且无赢家列 U。总场次 N 下报告得分区间 `[(W+0.5D)/N, (W+0.5D+U)/N]`，通过门槛以保守端及其置信下界判断，不能把 U 默认为半分、删除未决或只报已结束棋局胜率。
7. 困难与快速同条件同结果，自定义兼容通过；真机性能单独通过。离线达标但真机预算下不达标，仍只能称离线候选；优先减少节点成本和调度空闲，再评估计算时长。未测试或未接近 Win32 0.6 时，必须保留原生棋力目标未完成，不能只凭 JS 达标结束整个目标。

若棋力改善但超时，应先检查节点热点和评价成本；若更快却仍走弱棋，应检查上游行为偏差、战术覆盖和评价。若只胜旧版、对小巫师未达标，可如实标记“改进版候选，目标未完成”；若两项均无明确收益，保留旧版为默认，不以“重写完成”作为上线理由。
